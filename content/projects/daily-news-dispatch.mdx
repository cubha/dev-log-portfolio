# 📨 Daily News Dispatch — 보험·영업인을 위한 데일리 브리핑 자동 발송 SaaS

> **보험·영업인이 매일 손으로 만들어 고객에게 보내던 데일리 브리핑(날씨·미세먼지·환율·금값·뉴스·지수·유가·BTC·관심종목)을 자동 수집 → 템플릿 조립 → 카카오톡 발송까지 자동화하는 멀티테넌트 SaaS**
> 웹 대시보드(Next.js) + 상시 스케줄러 워커(node-cron) + 영업자 PC의 로컬 카카오톡 발송기(Python exe) 3계층 구조 · 월 구독 정기결제 · 현재 서비스명 「데일리 브리핑」

---

## ✨ 핵심 구현 내용

### 1. 📥 소스 어댑터 수집 파이프라인 — 실패를 숨기지 않는 계약
10여 개 공공·민간 데이터 소스를 단일 계약으로 추상화했습니다.
- **어댑터 계약**: 모든 소스가 `NewsAdapter` / `DataAdapter`를 구현하고, `FetchResult.status`(`ok` / `fallback` / `error`)가 대시보드·발송 로그까지 전파되어 폴백·실패가 화면에 드러남
- **데이터 소스**: 기상청 · 에어코리아 · 금융위(지수·주식시세·상장종목) · 특일정보 · 환율 · 금값 · 업비트 · 오피넷 · 네이버 검색 API + RSS
- **뉴스 하이브리드**: RSS(언론사 지정 가능, 키워드 검색 불가) + 네이버 검색 API(키워드 가능, 언론사 지정 불가)를 조합. 저작권 고려로 **제목·원문 링크만 저장**, 본문 컬럼 자체를 두지 않음
- **발송 시각 기준 소스 선정**: 수출입은행 환율은 11시 공시라 10시 발송에 항상 전일 값이 나감 → 1차 소스를 실시간 환율로 교체, 수출입은행은 2차 폴백
- **관심종목 축약 기사**: Claude API(Haiku)로 종목별 뉴스를 한 줄 요약

### 2. 💬 로컬 카카오톡 발송기 — Windows exe
알림톡·친구톡(사업자 채널 심사·건당 과금) 대신, 영업자 본인의 카카오톡 PC 앱을 직접 조작하는 방식을 택했습니다.
- **UI 자동화**: Python + pywinauto(Win32)로 대화방 검색 → 열기 → **창 제목으로 수신인 일치 확인 후에만 발송**(불일치 시 건너뜀). 실측 1인당 약 3.5초, 1회 상한 300명(서버 소유), 5건 연속 실패 시 자동 정지
- **서버 폴링 구조**: 초기에는 브라우저가 로컬 웹서버(127.0.0.1)를 호출했으나 Chrome의 Private Network Access 정책으로 차단 → 로컬 서버 모듈 8개를 철거하고 **exe가 서버 job을 폴링**하는 구조로 전환
- **단일 exe 배포**: GitHub Actions(windows-latest)가 PyInstaller onefile로 빌드 → GitHub Release 업로드 → 대시보드 다운로드 라우트가 스트리밍 제공
- **발송 명단 서버 소유**: 명단의 SoT를 로컬에서 서버(`Recipient`)로 이전하고 발송 화면을 대시보드 한 곳으로 통합

### 3. 🔐 기기 결착(Pairing) — 감지 대신 "인증 사실"
브라우저는 로컬 exe의 존재를 볼 수 없습니다. 그래서 "같은 PC인가"를 추측하지 않고 증명하도록 설계했습니다.
- **커스텀 URL 스킴** `dnd-agent://` — Windows 셸이 *그 PC에 등록된* exe를 실행하므로, "이 브라우저가 발급한 코드를 그 PC의 exe가 상환했다"는 사실을 OS가 보증
- **기각한 대안**: 공인 IP 대조 — 회사 노트북을 집 와이파이에 연결하면 집 데스크탑과 IP가 같아져 오판
- **자동 폴백 전면 금지**: 발송 기기를 임의로 골라주는 폴백을 없애 사고 유형을 "엉뚱한 PC에서 발송"에서 "조용히 미발송"으로 바꾸고, 그 미발송을 잡는 생존 게이트를 같은 Phase에 함께 배포
- PC당 1행(MachineGuid), 코드 상환은 단일 문장 원자적 쓰기 — 결정표 D-1~D-12 · Phase 1~8 전량 배포

### 4. 💳 구독 정기결제 — 상태 변경 주체는 하나
- 포트원 V2 + KCP 빌링키 기반 월 구독, 웹훅 서명(Standard Webhooks · HMAC-SHA256)을 라이브러리 없이 직접 검증
- **상태를 바꾸는 주체는 웹훅 하나뿐**: 크론은 청구만 시도하고 결과 반영은 하지 않음 — 둘 다 반영하면 구독 주기가 두 번 밀리는 경로를 구조적으로 차단
- 권한 판정을 두 축(운영자 부여 / 실결제)으로 분리해 체험·수동 부여와 결제 상태가 서로 덮어쓰지 않도록 설계

### 5. 🛡️ 품질 게이트 — 게이트에도 자기검사가 필요하다
- `verify.sh` + 커스텀 게이트 스크립트 11종: 사용자 문구 톤, Python ↔ TypeScript 상수 값 일치(parity), 색 토큰, 명암비 등
- 사용자 문구 **용어 사전(한 개념 = 한 낱말)** 을 문서화하고 게이트로 강제
- 테스트 `TZ=UTC` 고정 — 개발 PC가 KST라 **시간대 처리 코드를 지워도 1,160개 테스트가 전부 통과**한다는 사실을 뮤테이션으로 발견한 뒤 도입
- vitest 테스트 파일 200+ · Python 테스트 1,300+ 케이스, Railway 운영/개발 환경 분리 + 주간 DB 동기화

## 🚨 트러블슈팅

### 1️⃣ 발송기가 "연결 끊김"을 띄우는데 서버·토큰은 멀쩡함
* **문제 상황:** 발송기 창은 "연결 끊김 — 코드 재입력 필요"를 표시하는데 대시보드와 토큰은 정상. 처음에는 클라이언트 상태 관리 버그로 오진
* **원인 분석:** 같은 토큰으로 PowerShell 호출은 200, Python 호출은 403 — 이 대조로 범위를 좁힌 결과, 커스텀 도메인 앞단 Cloudflare Browser Integrity Check가 `Python-urllib/3.12` 기본 User-Agent를 봇으로 판정해 403(1010)을 반환. 접속 주소가 페어링 시점에 고정되므로 **도메인 전환 이후 새로 페어링한 사용자만** 겪는 잠복 결함이었음
* **해결 방안:** User-Agent를 단일 모듈로 모으고 호출부 9곳을 모두 경유시킴. AST로 `urllib.request.Request` 직접 생성을 전수 스캔하는 게이트를 추가하고, 스캐너가 실제로 9건을 찾는지 세는 **자기검사**까지 포함

### 2️⃣ 결제 청구 경로가 처음 실행되자 결함 6건이 한꺼번에 드러남
* **문제 상황:** 코드는 배포되어 있었고 단위 테스트도 모두 통과했지만, 실청구 기록은 0건 — 청구 경로가 실환경에서 한 번도 돈 적이 없었음
* **원인 분석:** 요청 본문 래핑 오류로 청구 100% 실패, 400 응답을 "카드 거절"로 분류해 *우리 버그가 고객 구독을 끊는* 경로, ID 형식 오류, 실패 응답에도 형식을 갖춘 필드가 와서 성공 판정이 오판, 호스팅 프록시가 502·504 응답 본문을 HTML로 바꿔치기, 청구 루프의 건별 예외 격리 부재
* **해결 방안:** 구독 주기를 과거로 당겨 크론이 즉시 실행되게 만들어 결함을 재현하고, 로그 접근이 없는 환경이라 인증된 임시 진단 라우트로 중간값을 수집 후 제거. 상태코드별 실측으로 프록시가 가로채는 코드를 특정해 앱 실패는 503으로 변경 — 6건 전부 수정

### 3️⃣ 외부 API 하나가 느려지자 요청 전체가 300초 뒤 502
* **문제 상황:** 오늘의 메시지 조회 API가 300초 대기 후 502로 끊김. 같은 토큰의 heartbeat는 1.2초에 정상 응답
* **원인 분석:** Node `fetch`(undici)에는 요청 전체 타임아웃이 없고, 소스별·지역별 수집이 **순차**로 겹쳐 있으며, 실패 시 대체값도 없었음
* **해결 방안:** `withRetry({ budgetMs })`로 재시도 횟수가 아닌 **시간 예산**으로 상한을 두고, `Promise.all` 병렬화로 13.3초 → 1.5초 단축. 실패 시 키 단위 최신값으로 폴백하되 등락 표시는 제거해 오해를 방지. 테스트에 "끝나지 않는 입력" 케이스 추가

### 4️⃣ 비대화형 `prisma migrate dev` 한 줄로 DB 데이터 소실
* **문제 상황:** `CI=true npx prisma migrate dev --create-only` 실행 직후 전 테이블이 0행이 되고 마이그레이션 이력 테이블도 사라짐. 스키마는 남아 있어 `COUNT(*)`를 직접 찍고서야 발견
* **원인 분석:** 스키마 드리프트 감지 시 뜨는 "DB 리셋" 확인 프롬프트를 `CI=true` 환경변수가 자동 승인
* **해결 방안:** 기존 마이그레이션을 `migrate resolve --applied`로 순서대로 재표시하고 미적용분만 `deploy`해 복구. 이후 `migrate dev` 사용을 금지하고 SQL은 `migrate diff`로 생성, 적용은 `deploy`/`resolve`만 사용. 적용된 마이그레이션은 체크섬(파일 바이트 SHA-256) 때문에 **주석 한 줄도 수정 금지**라는 규칙까지 확립

## 🤖 AI 협업 개발 구조

- **Claude Code (Controller + Implementer):** `/mvp` 파이프라인으로 첫날 scaffold → 순수 로직 → DB → 대시보드 → 라이브 연동까지 구축. 이후 기능 단위로 `/plan`(planner 위임) → `/sh-dev-loop`(TDD) → 배치 검증(verify.sh · scope-critic · acceptance-critic · db-schema-reviewer · security-auditor) → `/verify-impl` → `/ship` 파이프라인 운용
- **적대적 다중 검토:** 중대한 결정은 `/braintrust`로 정합성·실패모드·실행가능성·운영현실성 4개 렌즈의 에이전트가 교차 검토 — 로드맵 순서 결정에서 원안이 뒤집히기도 함
- **실기 검증:** WSL에서 Windows 데스크톱을 원격 조작해 exe의 카카오톡 발송을 실제 환경에서 검증
- **Claude API (런타임):** 관심종목 뉴스 축약 기사 생성

## 💡 회고

이 프로젝트의 아키텍처를 결정한 것은 코드가 아니라 **규제·약관·플랫폼 제약**이었습니다. SMS 대량발송의 광고성 규제 때문에 "나에게 보내기"로 파이프라인부터 증명했고, 카카오 공식 대량발송의 심사·과금 부담 때문에 로컬 발송기를 만들었으며, 결제대행사 계약 조건 때문에 일부 결제 수단을 폐기했습니다. "문서상 지원"과 "우리 계약에서 실제로 켜지는 것"이 세 번 어긋나면서, 외부 제약을 먼저 실측하는 습관을 얻었습니다.

가장 큰 교훈은 **"배포됐다"와 "한 번이라도 돌았다"는 다르다**는 것입니다. 모든 테스트가 초록불이던 결제 경로는 실청구 한 번에 결함 6건을 드러냈고, 시간대 코드를 지워도 통과하는 테스트, 파이프 종료 코드 처리 때문에 죽은 채 통과로 표시되던 게이트도 발견했습니다. 그 뒤로 모든 게이트에 "이 게이트가 실제로 잡는가"를 확인하는 자기검사를 붙였습니다. 1인 개발로 수집·발송·결제·로컬 에이전트까지 운영 가능한 SaaS를 완성한 것이 이 프로젝트의 핵심 성취입니다.
