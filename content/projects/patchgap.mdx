# 🔺 patchgap — 패치노트가 말한 것 vs 통계가 말하는 것

> **게임 공식 패치노트가 *말한 것*과 매치 통계·원본 게임데이터가 *실제로 말하는 것* 사이의 괴리(미공지 변화·간접 메타 이동)를 통계 게이트와 원천 링크로 보여주는 정적 브리핑 사이트**
> "26.18 패치노트는 12개를 바꿨다고 말했고, 통계는 62개 변화를 말한다." — LoL · TFT · PUBG 3개 게임 지원 · 원티드 AI 챔피언십 2026 출품작

---

## ✨ 핵심 구현 내용

### 1. 📥 수집·집계 파이프라인 — 런타임 외부 API 호출 0개
패치마다 대량의 매치를 무인 수집해 집계 JSON으로 커밋하는 구조를 설계했습니다.
- **LoL 수집 흐름**: KR 챌린저·GM·마스터 시드 → puuid → 패치 시간창 매치ID → 상세 전량 수집, 패치당 1만 매치 목표
- **내결함성**: JSONL reduce-on-ingest, 파일 단위 idempotent 재개, 429 `Retry-After` 재시도, `bottleneck` 2단 레이트리밋(20/1s ⟵ 100/120s)
- **재현 가능한 빌드**: 원본(`data/raw`)은 커밋하지 않고 집계 JSON만 커밋 → Next.js 정적 export(`output: 'export'`)로 빌드. 사이트 다운이 곧 대회 자격 위반이므로 **런타임 외부 호출 0**
- **네이티브 의존 0**: DuckDB 대신 순수 TypeScript 집계를 채택

### 2. 📐 통계 판정 엔진 — 승률 단독 판정을 버린 이유
2,000매치 기준 챔피언당 승률 CI 반폭은 ±9~10%p인데, 밸런스 변동은 1~3%p입니다. 노이즈에 묻히는 지표로 판정하지 않도록 설계했습니다.
- **1차 축 전환**: 승률 대신 픽·밴·아이템 채택률을 1차 판정 축으로 사용
- **다중검정 보정**: 승률은 n 게이트 + Newcombe CI 비중첩 + **BH-FDR `q < 0.10`**을 모두 통과해야 판정(170여 챔피언 × 다지표 동시 검정)
- **효과크기 바닥**: `EFFECT_SIZE_FLOORS`로 "통계적으로 유의하지만 실질적으로 무의미한" 변화를 걸러냄 — 7종 판정 체계
- **게임 무관 엔진**: 판정 엔진은 `{entity, metric, before, after, n}`만 받고, 게임별 어댑터가 이 형태로 정규화 → **TFT를 엔진 수정 없이 추가**
- Wilson · Newcombe · BH-FDR 직접 구현(외부 통계 라이브러리 0)

### 3. 🔗 패치노트 파서 + 2단 짝짓기 (결정론 → LLM)
- **파서**: cheerio로 패치노트에서 `{entity, skill, stat, before, after, direction}` + 원문 앵커 추출, `modeScope`로 다른 게임 모드 노트의 오매칭 차단
- **1단 결정론**: 엔티티 ID 블로킹 + 변화 방향 정합으로 먼저 매칭
- **2단 LLM(Claude)**: 짝이 없는 델타에만 간접 원인 추론 투입 — 반환된 노트 ID는 **입력 후보셋 안에 있을 때만 인정**, 검증 실패 문장은 회색(`--muted`) 처리. *판정은 LLM이 아니라 통계가 한다*
- **결정론적 캐시**: `sha256(model | promptVersion | deltaId | candidateSetHash)` 키, 예산 소진 시 캐시 폴백(크래시 없음)

### 4. 🕵️ 잠수함 패치 검출 — 패치노트에 없는 원본 수치 변경
- 게임별 원천 데이터 대조: LoL = Data Dragon, TFT = Community Dragon, PUBG = 텔레메트리 피해 격자
- "공지됨 / 미공지" 외에 **「공지값 불일치」**(말했는데 실제 값이 다름) 제3 상태 도입
- 실측 검출: TFT 18.3에서 4건(예: 마스터 이 AD 65→62), LoL 26.19에서 엘리스 R 1건
- PUBG 판별 임계는 **무변화 대조군**(같은 패치를 무작위 반분, D 최대 0.021)으로 결정

### 5. 🤖 무인 운영 — GitHub Actions 5종 + 패치 캘린더 자동 감지
- `collect`(LoL) · `collect-tft` · `collect-pubg` · `patch-watch` · `ci` 5개 워크플로우가 시간대를 나눠 일일 수집
- **패치 감지**: LoL·TFT는 다음 후보 패치노트 URL의 200/404, PUBG는 Steam 뉴스 API로 탐지 → 캘린더 오버레이에 자동 추가(기존 수기 캘린더를 역산 재현해 검증)
- `reportSkip(game, reason)` — 사유를 필수 인자로 강제해 "초록불인데 아무 일도 안 한" 실행을 드러냄
- 산출물 불변식 테스트(댕글링 노트 ID 0 등) + 3게임 화면 동등성 계약 테스트, `verify.sh` 6단 게이트(Spec → tsc → eslint → vitest → build → design-lint)

## 🚨 트러블슈팅

### 1️⃣ 문장만 다듬으라고 했는데 LLM이 판정을 뒤집음
* **문제 상황:** 문장 다듬기 재요청 응답을 통째로 채택했더니 인용 8행·confidence 3행이 바뀌고, Pyke 밴률 판정이 *미공지 → 간접효과*로 뒤집힘. 프롬프트에는 "근거는 그대로 두세요"라고 명시되어 있었음
* **원인 분석:** 재분류 단계가 원인 문장을 읽는 구조였고, **프롬프트 속 금지 문장은 아무것도 강제하지 못함**
* **해결 방안:** `mergeRepairedProse`로 LLM 응답에서 **문장만** 가져오고 근거·판정 필드는 원본으로 고정, 항목 수가 불일치하면 병합 자체를 포기. "산문 규칙은 계약이 아니다 — 강제는 코드가 한다"를 설계 원칙으로 확정

### 2️⃣ "근거 미확인" 한 문구가 서로 다른 세 상태를 덮고 있었음
* **문제 상황:** 미공지 47건 대부분이 "근거 미확인"으로 표시되어 LLM 모델 상향을 검토
* **원인 분석:** 캐시 키를 재계산해 분해하니 *호출 자체가 안 됨 14 / LLM이 검토했으나 후보 없음 22 / 비결정성 6*으로 갈림. 진짜 원인은 CI `actions/cache`가 `data/raw`만 보존해 **LLM 캐시가 매번 비어 있던 것**과 호출 상한(50)이 대상(113건)보다 작았던 것
* **해결 방안:** 상태별로 문구를 분리하고 LLM 캐시를 CI에서 보존, 상한 조정. 모델 상향은 Sonnet vs Opus A/B 결과를 본 뒤 별도로 결정

### 3️⃣ PUBG 피해 격자 판별 — 규칙을 다섯 번 고쳐도 오탐이 모양만 바뀜
* **문제 상황:** 무기 피해량 미공지 변경 판별 규칙을 수정할 때마다 오탐이 사라지지 않고 형태만 달라짐
* **원인 분석:** 1~4차는 저장 요약(top 8 값)이 **손실 압축**이라 규칙이 볼 정보가 없었고, 5차에서 격자값이 연속 분포라 "이산 격자점 이동"이라는 **모델 전제 자체가 틀렸음**을 확인
* **해결 방안:** "대표값 하나"를 보는 방식에서 **로그 구간 히스토그램 교집합 이동(분포 전체)** 비교로 전환, 판별 임계는 무변화 대조군으로 실측 결정

### 4️⃣ `gh secret set --body -` 가 시크릿을 문자열 "-"로 저장 → CI는 초록불
* **문제 상황:** PUBG API 키 등록이 성공으로 보고되고 수집 잡도 성공했지만 데이터가 들어오지 않음
* **원인 분석:** `--body -`는 stdin을 읽지 않고 **문자 "-"를 값으로 저장**. 게다가 API 클라이언트가 재시도 소진 시 `null`을 반환하고, 호출부가 이를 "표본 0 = 변화 없음"으로 해석해 실패가 성공으로 위장됨
* **해결 방안:** `--body` 생략 후 stdin 전달로 재등록, 시크릿 등록 후에는 **해당 키를 쓰는 잡을 실제로 실행해 검증**하는 절차로 변경

- **Claude API (런타임):** 간접 원인 추론·인용 검증에만 제한적으로 사용, 판정 권한은 통계 엔진에 둠

## 💡 회고

이 프로젝트의 중심 질문은 **"LLM을 어디까지 믿을 것인가"** 였습니다. 결론은 *판정은 통계가, 설명은 LLM이, 강제는 코드가* 하는 역할 분리였습니다. 프롬프트에 "근거는 건드리지 마"라고 적어 두었지만 LLM은 판정을 뒤집었고, 그 뒤로는 어떤 제약도 산문이 아니라 병합 함수·불변식 테스트·assert로 박아 넣었습니다.

또 하나의 교훈은 **"한 문구가 여러 상태를 덮는다"** 는 것입니다. "근거 미확인"이라는 한 줄 뒤에 호출 누락·후보 없음·비결정성이 섞여 있었고, 모델을 올리기 전에 상태를 먼저 세어 본 덕분에 진짜 원인(CI 캐시 누락)을 찾을 수 있었습니다. 선언 축(패치노트)은 항상 최신이어야 하고 관측 축(통계)은 그 위에 얹히는 부가 기능이라는 **두 축의 직교** 원칙을 지키며, 단일 게임에서 3개 게임으로 엔진 수정 없이 확장한 것이 이 프로젝트의 핵심 성취입니다.
